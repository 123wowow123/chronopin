# Goal

Turn one source (a web page, YouTube video, X post, market page, or a topic to research) into **one pin**: a dated event with a place, a cost when it has one, its company, pictures, several independent references, a cited summary and its tags. The same stages run whether the app's Anthropic key has credit or a Claude Code session does the reasoning by hand, so every stage below has a **contract** (inputs and output shape) that either driver can satisfy. See [Scrape without credit](../playbooks/scrape-without-credit.md) for the by-hand driver and [Scraping API](../api/scraping-api.md) for the service built on these stages.

# Principles

**Taste-profile reviews (owner, 2026-10-11).** Research and attach verified
tasting reviews to every consumable product's native taste profile so they
appear directly beneath its radar, using `PinTaste.reviews` through
`PUT /api/pins/:id/taste`. Each entry needs a verified source URL, reviewer/title,
a short accurate tasting excerpt and a publication date when established.
Label ambassador/promotional posts and reviews of another pack or formulation;
do not treat retailer descriptions or customer star aggregates as firsthand
tasting reviews. Preserve hand-set profiles and existing scores during a
review-only update. If no usable review is found, document the sources checked
and unresolved gap rather than inventing evidence. Verify the review section,
source links and excerpts beneath the radar on the live pin, and keep the
research evidence and taste snapshot synchronized. See the
[product-guide strategy](../../product-guide-strategy.md#native-taste-radar-on-every-product-pin).
This applies to all existing taste-profile pins as well as new pins. Backfill
empty review arrays without replacing scores or existing reviews; put a dated,
specific review gap in the visible `basis` when no suitable account can be
verified. The [October 11 audit](../../taste-review-audit-2026-10-11.json)
records every profile, new review sources and remaining research gaps.

1. **One pin per event, not per article.** The pin is the thing that happens (an opening, a launch, a release), dated to when it happens. The article is only its source. A roundup or listicle becomes many pins, each with its own deep link or product page as `sourceUrl`, never the shared article.
2. **Report only what a page supports.** Null is the right answer for a field the source does not state. The two exceptions are dates: a delay with no new date, and a future release with no announced date (see [Which date](#decision-rules)). Both are estimated and say so with `Estimated:` (see [Fields](fields.md)).
3. **Never type a URL from memory.** A reference, image or purchase link must have been returned by a fetch or search in this run. `sourceUrl` may be a URL found by search but never fetched (IMDb), and nothing else may be.
4. **Cost, date and place belong to the pin's own event.** A phase gets the phase's cost, the newest revision wins, and a place is where the thing is, not where its operator sits.
5. **Only the LLM calls wait for a session.** Everything that is not a Claude call runs the same with or without credit: the headless browser (rendered text, images larger than 150x150, embedded videos, headings), the page's own metadata (Open Graph, meta tags, JSON-LD), every keyless lookup (Wikipedia and Wikidata, AniList, Jikan, YouTube oEmbed and search, Kalshi), image top-up, studio HQ, threading and the save. The two Claude calls (field extraction, reference search) come back from the scrape as `llmTasks` for a Claude Code session to answer; see [Scraping without credit](no-credit-mode.md) and [Scrape without credit](../playbooks/scrape-without-credit.md).
6. **Every stage fails soft.** A failed image, reference, rating or lookup adds nothing and never aborts the scrape. Only the fetch of the source and the final save may fail the whole job.
7. **Use the real API to save.** A direct-SQL insert skips the live feed, search sync, duplicate checks, threading and tag sync. Save through `POST /api/pins`.
8. **Curators are per vertical.** Each content vertical posts as its own curator account (@GameDesk, @FilmDesk, @AnimeDesk, @TechDesk, @OddsDesk), so a batch is attributable.
9. **Every pin must add value of its own (AdSense "low value content").** On 2026-10-04 Google AdSense refused to show ads on chronopin.com for *low value content*: a site has to give "substantial unique value", show "ongoing curation and structural maintenance" and hold "genuine user interest". Google's spam policies count scraped, thin and mass-produced pages against a site. So a generated pin is not done because its fields are filled. It has to say something the source page alone does not: a summary written in our own words from several sources (never a paraphrase or copy of one article), the context a reader needs (what came before, what it changes, what comes next, how it compares), its place in a thread, and its dates, place, references, media and tags. A pin that is only a title, a line and one link must not be posted. In a batch, if one pin's summary could pass for its sibling's with only the name swapped, the batch is template filler; write fewer, richer pins instead. Keep posted pins current (dates, delays, results, updates) rather than leaving them stale.

Stages 2 to 5 run in parallel where they do not depend on each other: the extractor and the reference search start together, and the screen details start as soon as the extractor has named the work. Stage 6 waits for the references (it takes pictures from the day's articles) and stage 8 waits for the extracted fields.

# Decision rules

**Pin image storage.** All pin images and generated thumbnails belong in Azure Blob Storage, never Git (owner, 2026-10-08). Keep only blob URLs and provenance metadata in the repository. Use ignored temporary caches for downloads and uploads. Verify the public blob and update catalog and live pin references before removing an existing image file. Application icons and other UI assets remain repository assets.

**Restaurant food galleries.** When the restaurant publishes an official gallery of its food, take up to **six media total** for its pin, counting useful existing media toward the cap (owner, 2026-10-08, AnnaLena). Inspect and choose distinct food photos, preserve gallery attribution, store the photos in Azure Blob Storage, and attach them to the production pin. Record Azure blob URLs rather than checked-in image files. Avoid repeated views, logos and staff portraits when food photos are available. Seasonal gallery dishes need not match the current menu; say so. This extends the usual three-media target for restaurant pins. Follow [restaurant scraping](../../restaurant-scraping.md) for sourcing, provenance and live-image verification.

**Scores on every season in a thread** (owner, 2026-10-08, on Chicago Fire season 14, pin 6928). Creating or completing a TV/anime season thread includes checking every season pin for aggregate scores, not just the newest season. Store each available score as a `PinRating` with its own source, scale and season URL. Prefer published season scores; keep Rotten Tomatoes critics and audience scores separately named. A show's overall rating is not its individual seasons' rating. Where a season has no published aggregate, an arithmetic mean of its rated, already-aired TVmaze episodes may be used, clearly labelled **TVmaze episode average** with the number of rated episodes; leave unrated and unaired episodes out. An ongoing season's score is provisional and covers only the rated episodes available so far. Do not calculate a Rotten Tomatoes percentage from hidden like/dislike counts when the site publishes no score. Check all thread members on production after saving; a season with no supported score remains unrated, with the gap and sources tried recorded. The by-hand admin path is `POST /api/admin/db/PinRating` (or patch an existing source row), which expires the affected pin pages. The automatic screen lookup still only collects the score sources implemented in `screen.ts`; a by-hand thread batch must perform this full check itself.

**Which URL is the source.** A URL the owner hands over **is** the source, even when it is a rewrite of someone else's reporting (owner, 2026-09-22, of a Rundown write-up of a Reuters scoop: "yes swap"). Still follow its credit chain - the outlets it names go to the top of the reference list, where the evidence belongs - and offer the swap rather than making it silently. Choosing for yourself, prefer the publisher's own page for the event. A video is rarely the event: pin the thing it covers, dated from the official schedule, and cite the video as a reference or the source. When a scrape finds a video or article whose subject already has a pin, add it to that pin as a reference instead of making a second pin (duplicates are suggested and confirmed, see the duplicate checks).

**Which date.** `startDateTime` is when the event itself happens, not when construction began or the article ran. A scheduled event uses its official time (`scheduled`). A year alone is its last day (`estimated`, all day, `2027-12-31`), a month its last day. **An article about a future release is pinned on the release, not the article** (owner, 2026-09-26). When a page talks about something still to come - a film, season, album, game, product or opening that is announced, teased or reported - the pin's start date is **when that thing is predicted to come out**, never the day it was announced or the day the article ran. Use the official date when there is one (`scheduled`); otherwise predict it and mark it `estimated`, with `dateConfidenceReasoning` starting `Estimated:` and saying what the prediction rests on: a stated window (a year, season or quarter, dated by the span rule above), a studio's own schedule or promotional reel, a distributor or box-office listing, the franchise's cadence (the gap between earlier instalments, the usual release weekday and season), and credible trade reports - naming which are unconfirmed. Title it as the release ("... Part 2 Releases in Japanese Theaters", "... Season 3 Premieres"), not "... Announced"; the announcement is a bullet in the summary. Re-date the pin to the real day once it is announced. Example: Demon Slayer Infinity Castle Part 2 (1774) and III (1766) were "Announced" pins on 30 Jun 2024 and now sit on about 16 Jul 2027 and 20 Jul 2029 - Part 1's Friday-in-July slot two and four years on, from ufotable's reel ruling out 2026, a September 2027 Crunchyroll listing and reports of a 2027/2029 cadence. A rumour or report about something that is not a release (a deal, a hire, a ruling) with no fixed date is still anchored to the article's `article:published_time`. A prediction market's date is the day its daily market prices highest (`estimated`) or its strike time when scheduled. Dates are UTC; an all-day pin starts 00:00Z and ends at the exclusive 00:00Z after its last day.

**Predictions use the predicted start** (owner, 2026-10-08, on pin 5097). Pin the forecast event, with a title and description about that event, on its most likely onset, `estimated`, never on the forecast publication, next bulletin or market settlement. Use a stated most likely start; otherwise choose the best-supported forecast window and use its first day, explicitly explaining the window boundary rather than claiming an exact day. For a forecast period of conditions, keep the exclusive end after its last day. This overrides the general last-day span rule and the article-date fallback for rumours above. Mutually exclusive dated outcomes: highest probability; cumulative "by" ladders: largest probability increase between adjacent rungs. A lone deadline with no onset evidence is only an estimated bound, and the reasoning says so. Quote the window and odds in `dateConfidenceReasoning` starting `Estimated:`; odds are not certainty about a day. References must date the same forecast event, not the bulletin. Example: historic El Niño forecast for October-December 2026 starts `2026-10-01T00:00:00Z`, ends `2027-01-01T00:00:00Z`, estimated; NOAA's October 8 discussion is not its start. Only a pin explicitly about publishing a bulletin uses that bulletin's scheduled date.

**An undated source is dated from all the sources** (owner, 2026-09-30: "estimated dates are fine and scraper should have ability to estimate dates based on all the sources"). When the source page gives no date, do not leave the pin undated and do not stop at the page: weigh the references too - their own stated dates, publication times, schedules and calendars, the cadence of earlier occurrences - and take the best-supported day as `estimated`, `dateConfidenceReasoning` starting `Estimated:`, naming the sources it rests on and saying which are unconfirmed. A firmer source (an agency calendar) outranks a looser one (a news article's "later this year"). Built in [estimateDate.ts](../../../src/server/scrape/estimateDate.ts) for the case where a reference names a day (see [Learnings](learnings.md)); when no reference names a day, one more model call ([estimateDate.ts](../../../src/server/extract/estimateDate.ts)) estimates from the source and every reference together (windows, schedules, cadence), and returns nothing rather than a guess.

**Which cost.** The headline cost fully expanded (`CA$6.4 billion` is `6400000000`, `CAD`), matched to what the title says is happening: a programme's total for a programme, a part's own figure for a phase, line, terminal or building. Take the newest estimate, the midpoint of a range, and never trade volume, revenue or budgets. A film or game release carries no price (budgets and grosses go in the summary). Null when genuinely costless.

**How much money is on a market.** A prediction-market pin records what the market has traded, in dollars, as well as what it prices. Volume is how a reader tells a market that means something from a market with four bets on it, and a market with $15M behind its 30% is a stronger claim about the world than one with $900. So:

- **Quote it in the summary or description**, beside the odds it supports ("traders give $3,500 a 30% chance on a book that has turned over $15M"), and quote it per market when the pin cites more than one. A figure under about $10,000 is worth saying out loud as a caveat rather than left for the reader to find.
- **Where it comes from.** Polymarket reports dollars directly (`volume` on the event and on each market in the Gamma API; `volume24hr`, `volume1wk` and `volume1mo` say how much of it is recent). Kalshi counts **contracts**, not dollars: `volume_fp` on each nested market, which becomes money as contracts x their last price (`last_price_dollars`) - an estimate at today's price, and the figure the site and the pin page both show. Polymarket US publishes no volume at all, so a pin citing only that exchange has none to quote.
- **Never pass volume off as the pin's `price`.** The cost rule above stands: a market's turnover is not the event's cost, and a market pin has no `price`.
- **The pin carries the figure itself.** Once saved, `Pin.marketVolume` holds the dollars across every market the pin's source and references link (schema 0053, [pinMarketVolume.ts](../../../src/server/services/pinMarketVolume.ts)). It is written on save and edit, kept up as anyone watches the pin's odds, and refreshed in bulk by `npm run markets:volume -- --apply`; nothing an author types sets it. The pin page shows it beside the pin's other facts, and the timeline's bag weight lifts a pin for it ([bagSample.ts](../../../src/lib/bagSample.ts)), so a busy market earns its place on a crowded day. That is automatic - the curator's job is only to pick markets worth citing and to say what they have traded.
- **Prefer the liquid market** when two exchanges list the same question, and when a ladder's rungs quote out of order, the liquid rungs are the ones to date the pin from.

**Which results table.** A pin about an AI model (or any product whose maker publishes a headline results table) carries that table: after the notable-features list, `<h3>Benchmarks</h3>` and an HTML `<table>` with the maker's own rows, columns and cell notes ("with tools", "partial"), cited to where it was read. Owner, 2026-09-28, on Claude Sonnet 5.5, and again 2026-09-30 on Gemini 4 Argon (pin 5023 shipped without it: "for this and other model we should include main performance table if available"). Where to look, in order: the maker's model card or announcement page (Google: `deepmind.google/models/model-cards/<model>/` and the tables on `deepmind.google/models/gemini/`; Anthropic and OpenAI: the launch post), then its evals-methodology page. Keep the maker's columns (the model, its predecessor, the rivals it names) and skip a table that is only a price list the features already give. A release with no published table (a bar chart only, or a preview with none yet) gets none, and `_notes` says so. Footnote markers go in as Unicode superscripts, since the sanitizer strips `<sup>`. Full write-up: learnings 2026-09-28 ("The maker's main results table goes on the pin").

**Which company.** The single organisation the event is chiefly about or done by: a product's maker, a project's owner or operator, an agency for a mission. For film, TV, anime and games it is the studio or developer, never the publisher, broadcaster or streamer. Reuse an existing company by exact name (a rename is merged into the older row).

**Which category.** Only from the fixed list in [categories.ts](../../../src/lib/categories.ts), closest fit first. Every name is **one word**, so give a pin every word it is squarely about rather than one broad word: a film is `Movie`, a TV show `TV`, an anime film `Anime` and `Movie`, a new metro line `Transport`, a museum opening `Architecture` and `Art`. There is no "Other" - add a specific word to the list instead.

**Which references.** Official announcement or press release first, then filings and government pages, then established news or trade press. Skip the source itself, aggregators, forums, social posts and SEO farms, and anything that only rewrites other coverage. A reference's `startDate`/`endDate` move the pin's dates, so leave them null unless the page firmly dates the event.

**Which media.** Make a best effort to reach **3 media** on every pin, **at least 1 of them a video and at least 1 a picture**: work down the sources in order and do not stop at the first one that adds a single picture. The page's own picture stays the default heading and the rest follow it. A video is a medium too and is now required: take one embedded on the page, else the maker's own launch or keynote video, a trailer or a verified-channel demo found with YouTube search (verify the channel and that it is the right work; a fan channel or the wrong title is worse than none), and add its still as a picture when the page had none. If every source is exhausted with fewer than 3, or with no video, save what was found and record in the job what was tried; never pad with a URL that was not fetched, an unrelated stock picture or a duplicate.

**Ticket buttons.** An attendable event pin (`isAttendableEvent` in [seo.ts](../../../src/lib/seo.ts): Conference/Festival always, Sports or timed Music unless also Business/Law/Fashion/Movie/Anime/etc.) gets a `PUT /api/pins/:id/event-info` whenever the organiser's or ticketer's own page is readable, not only at conventions - a concert, festival, sporting fixture or expo gets the same reading. Fields: `ticketUrl` to that **specific show's** purchase page, never the tour index, artist page or a resale marketplace; `availability` (`InStock` once the page says on sale, `SoldOut`, `PreOrder` with no link for "coming soon"); low/high price + `priceCurrency` only when the page states them for this edition; `source: hand` (by-hand `ev.py`-style write) or `session` (a Claude Code session's own reading); `sourceUrl` = the page actually read. Same rule as references and media - never type a link from memory; it must come from a fetch of that page in this run. For Ticketmaster specifically: the **artist** page's `schema.org` `Offer` per show carries the per-event URL and whether it shows availability ("NO AVAILABILITY"/"LOW AVAILABILITY" is not `SoldOut` wording - leave it `InStock`, not unsaved); the per-event page itself returns no usable text. A pin with no ticket page to read, or one that is only a save-the-date or newsletter form, is left without a `PinEventInfo` row rather than guessed. The daily `eventInfo` job (see [Daily jobs](daily-jobs.md)) re-checks every attendable pin on roughly this same basis once it exists, so a scrape that cannot read the ticket page yet is not a dead end.

**Watch buttons.** A film, TV or anime pin's "Watch on Netflix/Crunchyroll/HIDIVE..." buttons (`Merchant` rows, see [Enrichment](enrichment.md#film-tv-anime-and-game-extras)) are stage 4's job, and stage 4 only runs **at creation**, only when the pin already carries a screen category (Anime/Movie/TV/Game) at that moment (`isScreenCategory` in [index.ts](../../../src/server/scrape/index.ts)). Neither `PUT`/`PATCH /api/pins/:id` nor any daily job re-runs it afterwards - unlike ticket buttons, which the `eventInfo` job rechecks twice a day (see [Daily jobs](daily-jobs.md#eventinfo)). Two known gaps this leaves: (1) a pin created before its screen category is added (an edit, or the daily categoriser) never gets watch links, ratings, episode count or a trailer unless the backfill is run by hand (owner found this 2026-10-01 on pin 861, "Reincarnated as a Sword Season 2 Premieres" - created 2026-09-15 as Anime desk's pin but tagged `Anime` only on 2026-09-19, so stage 4 never fired; `npm run media:screen -- --ids <id> --apply` or a by-hand `POST /api/admin/db/Merchant` row fixes one pin after the fact); (2) a title that gains a new streaming deal after its pin was made stays stale until the next manual backfill. Owner's instruction (2026-10-01): **watch buttons should be (re-)added whenever a pin is inserted or updated**, not only at first creation - fold this into stage 4 (or the update path) and/or give streaming its own daily recheck job the way `eventInfo` does for tickets, so a pin that becomes Anime/Movie/TV/Game later, or whose streaming availability changes, is not stuck without a watch button until someone remembers to run the backfill. Not yet built; tracked here until it is.

**Game facts.** A game pin carries three things beyond its trailer (owner, 2026-10-04, on GTA V's pin 5455, from a Steam page's age-rating box): its **aggregated rating**, its **maturity rating** and its **supported platforms**. Ratings are `PinRating` rows from every source that lists the game (Metacritic, Steam user reviews, OpenCritic where readable), each in its own scale and linked to the page it came from, so the pin's average works as it does for films. Maturity is the rating board's label (ESRB "Mature 17+", or PEGI 18 where that is the board shown) **with its content descriptors** ("Intense Violence", "Blood and Gore", "Strong Language", "Use of Drugs and Alcohol"), read from the Steam store page, the board's own listing or Wikidata, and saying which board it is. Platforms are the ones the game actually ships on (Windows, macOS, Linux, PlayStation 5, Xbox Series X|S, Switch ...), not the ones a store page happens to be open on. Each platform is **shown with its official logo** (Windows, Apple, Linux, PlayStation, Xbox, Nintendo Switch, Steam Deck ...) with the name as its label, never as plain text alone; the stored value is a fixed platform key, so the logo lookup cannot miss on spelling. Same rules as everything else: read from a page fetched in this run, null when no source states it, never typed from memory, and a failed lookup adds nothing. Built: `PinGameInfo` (schema 0124), read from the pin's Steam page plus Wikidata (`src/server/gameFacts.ts`) right after a pin is saved, and backfilled with `npm run games:info [-- --ids a,b] [--apply] [--out f.json]`; `PUT /api/pins/:id/game-info` stores a reading on another database (prod).

**Taste profile (owner, 2026-10-10, 2026-10-14).** Every consumable food, snack and beverage product pin (a snack, confectionery, food launch, cider, beer, spirit or wine release; not a restaurant, a company's results or a law about alcohol) must carry its seven-axis taste rubric: **Aroma 香り, Bitterness 苦味, Sweetness 甘味, Astringency 渋味, Umami うま味, Pungent 辛味 (chilli, pepper, ginger, the bite of strong spirit), Coolness 清涼感 (mint, menthol)**, each 0-5 in half steps, as well as verified firsthand tasting reviews (`PinTaste.reviews`) attached beneath the radar. A drink also carries its **alcohol by volume** (`abv`, with `abvSourceUrl` when the pin's own source is not the page that states it): a stated fact, filled only from a page that gives the figure for that exact product, never for a lineup or a barrel-variable release. Scores are an **editorial estimate** with a one-sentence **basis** explaining what the ratings rest on (tasting notes, ingredients, ABV, or style). Save through `PUT /api/pins/:id/taste` across both local and production environments, and keep `scripts/products/taste.json` synchronized. Built: `PinTaste` (schema 0157, abv 0158/0159, pungent and coolness 0160), `PUT /api/pins/:id/taste` (`source` `session` or `hand`; a `hand` row is never overwritten by an estimate), the radar in `src/components/pin/PinTaste.tsx`, and the snapshot `scripts/products/taste.json` stored with `npm run products:taste [-- --apply] [--out f.json]` (`--out` writes the bodies to PUT to prod).


**Car performance rubric.** A vehicle pin (a new EV, EREV or PHEV model's launch) can carry a seven-axis radar, the sibling of the taste radar (`PinCarPerf`, schema 0167, 0187): **Range, Charging, Acceleration, Driver assist, Space & comfort, Value, Kids friendly**, each 0-5 in half steps, headed "Car performance rubric" and labelled "Estimate" on the pin page. The scores are editorial estimates computed from the model's **published** specs and price against the anchors below (the 2026 edition, see "Rubric year"); interpolate between anchors to a half step. Score the headline or launch variant the pin is about, use the same variant for every axis and name it in the `basis`. Never guess a spec from a rival: when the figure for an axis is not published for the model, store `null` for that axis (the radar draws it as "n/a" at the centre and leaves it out of the shape) and say so in the `basis`. A rubric needs at least one score.

| Axis key | Label | What it measures | Anchors (interpolate to a half step) |
|---|---|---|---|
| `range` | Range | Official range of the headline variant (CLTC km as published; for EREV/PHEV use the stated total/combined range, and say it is CLTC) | <250 km = 0.5, 300 = 1, 450 = 2, 600 = 3, 800 = 4, >=1000 = 5 |
| `charging` | Charging | Fast-charging capability: peak DC power or 10-80 % time as published | no DC fast charge = 0, <=60 kW or >40 min = 1, ~100 kW / 30 min = 2, ~200 kW / 20 min = 3, ~400 kW / 12 min = 4, >=600 kW or <=8 min (megawatt/5C-6C+) = 5 |
| `acceleration` | Acceleration | Published 0-100 km/h time (or 0-96 km/h) of the headline variant | >=10 s = 0.5, 8 = 1.5, 6.5 = 2.5, 5 = 3, 4 = 3.5, 3 = 4.5, <=2.5 = 5 |
| `assistance` | Driver assist | Driver-assistance hardware/software published for the car | none or basic ACC/LKA = 1, L2 highway pilot, no LiDAR = 2, urban NOA camera-based = 3, LiDAR + large compute (Orin-X/Thor, Huawei ADS 3+, Momenta, Xiaomi HAD) with city NOA = 4, flagship dual-compute / L3-capable hardware or permit = 5 |
| `space` | Space & comfort | Size and cabin: wheelbase, seats, comfort hardware (air suspension, 2nd-row luxuries) | micro/kei or <2,500 mm wheelbase = 1, compact 2,600-2,700 = 2, mid 2,800-2,900 = 3, large 2,950-3,050 or 6-seat = 4, >=3,100 mm or luxury MPV/executive with air suspension and rear lounge = 5 |
| `value` | Value | Price against what the spec sheet delivers vs same-segment rivals at the launch price | priced above comparable rivals = 1, at market = 3, clearly undercuts rivals on stated specs = 5 (name the comparison in `basis`) |
| `kidsFriendly` | Kids friendly | Family and child suitability: ISOFIX child seat anchors, rear cabin space, climate vents, rear entertainment, child safety locks/presence detection, stroller trunk capacity | 2-seater or no child accommodation = 0.5, tight 2+2 or minimal rear child space = 1.5, compact with standard ISOFIX = 2.5, standard 5-seat family sedan/crossover with dual ISOFIX and rear vents = 3.5, spacious family SUV with rear climate zones, sunshades and large stroller boot = 4.5, dedicated flagship family vehicle/MPV with rear cinema screens, multi-zone ISOFIX, fridge/bottle warmer, zero-gravity seats, baby sleep modes = 5 |

**Dining rubric.** A restaurant pin (any guide city: new openings, top restaurants, specials) can carry a five-axis radar, the sibling of the taste and car performance radars (`PinDining`, schema 0170): **Food, Service, Ambience, Value, Critic acclaim**, each 0-5 in half steps, headed "Dining rubric" and labelled as an editorial estimate on the pin page. The first four are read from the venue's **published diner sub-scores** - OpenTable prints exactly Food / Service / Ambience / Value out of 5, so use those when the venue has them, and otherwise Google / Yelp / Tabelog / the local equivalent, each rescaled to 0-5 - cross-checked against independent reviews. Critic acclaim is read from published recognition only. Never infer a score from the cuisine, the price tier or a sister branch; when no figure is published for an axis (a restaurant that opened last week has no diner scores) store `null` for it - the radar draws "n/a" at the centre and leaves it out of the shape - and say so in the `basis`. A rubric needs at least one score. There is no rubric year: the anchors are published scales, not a spec benchmark that moves.

| Axis key | Label | What it measures | Anchors (interpolate to a half step) |
|---|---|---|---|
| `food` | Food | The venue's own diner food score (OpenTable Food, or the platform's food/overall score rescaled) and what reviews say of the cooking | <3.5/5 = 1.5, 4.0 = 2.5, 4.3 = 3.5, 4.6 = 4.5, >=4.8 with consistent praise in independent reviews = 5; fewer than ~30 ratings: cap at 3.5 and say so |
| `service` | Service | OpenTable Service (or platform equivalent) and review comments on service | same scale as `food` |
| `ambience` | Ambience | OpenTable Ambience (or platform equivalent), room, noise and setting as reviews describe them | same scale as `food` |
| `value` | Value | OpenTable Value (or platform equivalent); where only price is known, leave `null` rather than guess | same scale as `food` |
| `acclaim` | Critic acclaim | Recognition by a published guide or award, current edition, for this venue (not the group) | none found in a city a guide covers = 0, listed in a guide (Michelin Guide listing, Gault&Millau, Tabelog Award, Time Out/Eater best-of) = 2, Bib Gourmand or Michelin Plate or national best-of award = 3, 1 Michelin star or regional-list top 50 = 4, 2 stars or world/Asia 50 Best top 50 = 4.5, 3 stars or 50 Best top 10 = 5; guide not covering the city = `null`. Other recognition, interpolated on the same scale: James Beard Foundation Restaurant and Chef Award winner (restaurant-level) = 4, James Beard America's Classics = 3, a continent-level or niche best-of (World Culinary Awards, Wine Spectator Grand Award alone) = 2-2.5, a past edition's stars are not counted. A source that could not be read (guide site blocked, search unreliable) leaves the axis `null`; do not turn "not found" into 0 unless the guide's own page for the city was searched and read |

Output per pin: `{pinId, scores:{food, service, ambience, value, acclaim} (numbers or null), basis (one or two sentences, at most about 600 characters, naming the figures that drove each score - platform, rating, review count - and any null), sourceUrl (the page the diner scores or recognition came from), reviews (optional, as for the car rubric: https pages reviewing this venue, at most 6, a verbatim quote of at most 300 characters, every URL opened in this run)}`. Built: `PinDining`, `PUT`/`GET`/`DELETE /api/pins/:id/dining` (the flat body `{food, service, ambience, value, acclaim, reviews, source, basis, sourceUrl}`, all five axis keys required, `source` `session` or `hand`; a `hand` row is never overwritten by an estimate), the radar in `src/components/pin/PinDining.tsx` (drawn by `TasteRadar`), and the search terms `dining:<axis>` (score 3 or more; a null axis never matches) and `dining:any`. Nothing is scored until a person or a session stores a row: do not backfill from the menu or the price.

**Hotel rubric.** A hotel or resort pin (an opening, a reopening, a rebrand) can carry a six-axis radar, the sibling of the dining radar (`PinHotel`, schema 0174): **Rooms, Service, Location, Cleanliness, Value, Critic acclaim**, each 0-5 in half steps, headed "Hotel rubric" and labelled as an editorial estimate on the pin page. The first five are read from the property's **published guest sub-scores**: Booking.com prints Comfort, Staff, Location, Cleanliness and Value for money out of 10, so halve them (Rooms from Comfort/Facilities, Service from Staff); where it has none use Google or Tripadvisor rescaled to 0-5, cross-checked against independent reviews. Critic acclaim is read from published recognition only (Michelin Keys, Forbes Travel Guide stars, AAA diamonds, Relais & Chateaux, Conde Nast / Travel + Leisure lists); 0 only where a guide covers the destination, otherwise `null`. Never infer a score from the star class, the room rate or a sister property; a hotel that opened last week has no guest scores, so store `null` for the axis, say so in the `basis`, and let the radar draw "n/a". A rubric needs at least one score. There is no rubric year: the anchors are published scales, not a spec benchmark that moves.

**Acclaim is always checked (owner, 2026-10-13).** Never leave `acclaim` null because a pass "did not check" the guides. For every hotel rubric read all three: the MICHELIN Guide (Keys and the "New" badge, with the selection year; guide.michelin.com loads through WebFetch, not curl), Forbes Travel Guide (star rating or "Soon to be Rated"; JS-rendered, use Chrome) and AAA Diamonds (USA, Canada, Mexico, Caribbean). The basis names what each said and the year. `null` is allowed only when no guide covers the destination or a guide could not be read after trying, and the basis then names which. A resort-level rating does not count for a named tower or sub-property. A hotel too new to be rated is `0` where a guide covers the destination and has not listed it, with "Soon to be Rated" or "New" noted in the basis.

Built: `PinHotel`, `PUT`/`GET`/`DELETE /api/pins/:id/hotel` (the flat body `{rooms, service, location, cleanliness, value, acclaim, reviews, source, basis, sourceUrl}`, all six axis keys required, `source` `session` or `hand`; a `hand` row is never overwritten by an estimate; reviews as for the dining rubric), the radar in `src/components/pin/PinHotel.tsx` (drawn by `TasteRadar`), and the search terms `hotel:<axis>` (score 3 or more; a null axis never matches) and `hotel:any`. Nothing is scored until a person or a session stores a row: do not backfill from the star class or the room rate.

**Wiki backing for a dining rubric.** A score is only as good as the page it was read from, so every page a rubric's figures came from is made one of the pin's references (the rubric's citation then reads `[n]` into the References panel) and gets a link wiki: a short page stating the figures as read, the date read, and how the pin's scores use them (and any figure deliberately not used, e.g. an implausible OpenTable Value). The Michelin or guide page is usually a reference already. `npm run restaurants:dining` (`scripts/restaurants/diningRubric.ts`, list in `scripts/restaurants/diningRubric.json`) stores the rubric, adds each entry's `sources` as references (credited to the admin account, skipping links the pin has) and saves their wikis through the prebuilt-wiki path (`applyPrebuiltWikis`, no fetch and no model call; a pin's summary is not rebuilt). Run it on a database whose pin ids the list was written against; for prod, PUT the rubric to `/api/pins/:id/dining`, POST the references, and send the wikis to `/api/admin/source-wikis` (a script run directly against a database cannot expire a running server's pin-page cache, so a page may show the old citation for up to the cache hour).

**Rubric year (every engineering performance rubric).** An engineering rubric (cars now; ships, aircraft or batteries when they get one) scores a spec against anchors, and the anchors move: a 2026 "5" for range will be a 2028 "4". So every engineering performance rubric carries the **year of its criteria**, `rubricYear` (`PinCarPerf.rubricYear`, schema 0169, a whole year 2020-2100), and the pin page labels it ("2026 criteria", next to the "Estimate" pill, with a note that scores are only comparable within one year); the pill is a search link to `rubric:<year>`, the pins scored against that year's criteria. Rules: (1) the anchors above are the **2026 edition**; when they are tightened, bump `CAR_PERF_RUBRIC_YEAR` in `src/lib/pinCarPerf.ts` and write the new table as a new edition here, keeping the old one, never editing the 2026 anchors in place; (2) a row keeps the year it was scored under: an older edition's scores are **kept, labelled, not rescored silently**, and are re-scored deliberately by saving the row again with the new year (which overwrites it); (3) never compare, rank or average scores of different years, and when the source figures behind an old row are no longer available leave it at its year rather than guess; (4) a body or entry with no `rubricYear` is the current edition on a new row and keeps the stored year on an existing one (the `products:carperf` script always writes the year, so put `"rubricYear"` on every entry). Validation is `rubricYearProblem` in `src/lib/rubricYear.ts` and the pill is `RubricYearPill`, both shared so the next engineering rubric reuses them; the search term `rubric:<year>` (a whole year 2020-2100, anything else is left out; several years widen each other) matches a pin with a rubric of that year in **any** engineering rubric table, and a new rubric joins it by adding its table (with `pinId` and `rubricYear`) to `RUBRIC_TABLES` in `src/server/util/rubricSearch.ts`; the taste radar is a judgement of flavour, not a spec benchmark, and has no year.

Output per pin: `{pinId, rubricYear (the edition scored against, 2026 today), scores:{range, charging, acceleration, assistance, space, value, kidsFriendly} (numbers or null), basis (one or two sentences, at most about 600 characters, naming the figures that drove each score, the variant scored and any null), sourceUrl (the page the spec figures came from), reviews (optional, see below)}`. Every figure must come from a page that was opened; the pin's draft already carries the sources in its references. A pin has a taste profile or a car performance rubric, not both. Built: `PinCarPerf`, `PUT`/`GET`/`DELETE /api/pins/:id/car-performance` (the flat body `{range, charging, acceleration, assistance, space, value, kidsFriendly, reviews, rubricYear, source, basis, sourceUrl}`, all seven axis keys required, `source` `session` or `hand`; a `hand` row is never overwritten by an estimate), the radar in `src/components/pin/PinCarPerf.tsx` (drawn by `TasteRadar`), the search terms `carperf:<axis>` (score 3 or more; a null axis never matches) and `carperf:any`, which combine with `rubric:<year>` (`carperf:range rubric:2026`: the year is read off that same car rubric), and the snapshot `scripts/products/carPerf.json` stored with `npm run products:carperf [-- --dry] [--out f.json]` (entries for pin ids that do not exist in the database it runs against are skipped and counted; `--out` writes the bodies to PUT to prod).

**Car performance reviews.** Like the taste profile's tasting reviews, a car performance rubric can carry the independent reviews it was checked against (`PinCarPerf.reviews`, schema 0168; `PinGasCarPerf.reviews`, schema 0173), listed under the radar by the same `ReviewList` component. Each entry is `{url, title, publishedDate, quote}`: an `https` page that is a road test, hands-on review or long-term test of **this model and variant** (not the launch announcement, a press release, a spec aggregator, or a review of another trim or market), the review's own headline as `title`, its publication day as `YYYY-MM-DD` (or `null` when the page does not state one), and a short verbatim extract as `quote` of at most 300 characters. Aim for at least **3 verified independent reviews** per vehicle pin (at most 6, best first). Every URL must have been opened in this run and the quote copied from that page, never recalled; label a manufacturer-sponsored or invited-drive piece in the `title`. A rubric with no usable review is saved without any (the pin shows none) and the sources checked are noted in the research notes. Stored with the rubric: `PUT /api/pins/:id/car-performance` or `PUT /api/pins/:id/gas-car-performance` with a `reviews` array replaces the list, a body with no `reviews` key keeps the pin's existing reviews and `reviews: []` clears them; a `reviews` array in an entry of `scripts/products/carPerf.json` goes through `npm run products:carperf` the same way (no key keeps, `[]` clears; `--out` writes the key only when the entry has it). The shape and limits are validated by `reviewsProblem` in `src/lib/pinReviews.ts`, shared with `PinTaste.reviews`; reviews are not `PinReference` rows because those are date evidence.

**Gasoline car rubric (2026 edition).** A gasoline (ICE or mild-hybrid) model's launch pin can carry its own six-axis radar (`PinGasCarPerf`, schema 0173; `GET/PUT/DELETE /api/pins/:id/gas-car-performance`, body `{power, acceleration, economy, handling, space, value, reviews, rubricYear, source, basis, sourceUrl}`; same rules as the electric rubric: half steps, `null` = not published, never guess from a rival, score the headline/launch variant and name it in `basis`, reviews are opened pages with a verbatim quote). Shown on the pin as "Car performance rubric" and ranked on `/cars` ("Best gasoline cars", average of the scored axes, at least 4 scored). Anchors (interpolate to a half step):
- **power** (peak output of the scored variant, hp/PS as published): 600+ = 5; 450 = 4; 300 = 3; 200 = 2; 150 = 1; under 120 = 0.
- **acceleration** (0-60 mph or 0-100 km/h, the maker's figure, else an independent test; say which): 3.0 s or less = 5; 4.0 = 4; 5.5 = 3; 7.5 = 2; 9.5 = 1; over 11 = 0.
- **economy** (combined: EPA mpg, else WLTP/NEDC converted, say which; a mild-hybrid counts as published): 45+ mpg = 5; 38 = 4; 30 = 3; 24 = 2; 19 = 1; under 15 = 0.
- **handling** (no spec exists, so it rests on independent road tests only: skidpad/slalom figures or the consensus of at least two reviews of this model): class-leading = 5; praised = 4; competent = 3; average = 2; criticised = 1; poor = 0; `null` when fewer than two road tests exist.
- **space** (cargo litres/cu ft and rear-seat room against its class, or the usable space the maker publishes): class-best = 5; above average = 4; average = 3; below = 2; cramped = 1; a two-seat sports car is scored against two-seaters (cargo only) and says so.
- **value** (peak hp per US$1,000 of the base price of the scored variant, or the local-currency equivalent against the same market's hp/price; say which): 12+ = 5; 9 = 4; 7 = 3; 5 = 2; 3.5 = 1; under 3 = 0.
The 2026 anchors are never edited in place: tightened anchors become a new edition and `GAS_CAR_PERF_RUBRIC_YEAR` (src/lib/pinGasCarPerf.ts) is bumped. Scores of different years are never compared.

**Which pins respond to which.** Dated variants of one product (the colorways of a shoe, the trims of a car) form one linear chain ordered by date, oldest first: each pin's `parentId` is the previous pin, and the first has `parentId: null`. Pins on the same day keep the source's own order. Post them all first, then set the chain with a `PUT` per pin that carries the full pin body (media and references are re-saved wholesale, so send them back). Same rule as [series](../../../src/server/scrape/prequel.ts): one chain, never a branch. This holds for any run of pins about one recurring thing, not only products: a schedule of dated launches (SpaceX) is one chain across rockets in launch-time order but **newest first**: the latest launch is the head and each launch answers the one *after* it, so the oldest launch has the highest response number (the owner's rule for schedules; product variants and story series stay oldest first). Re-running the scrape re-chains, so a launch pinned later slots into place; a scraper that sets the chain itself does it after all the pins exist, by a `PUT` of each whole pin (`chainLaunches` in [launches.ts](../../../scripts/spacex/launches.ts)); never a direct `UPDATE` of `parentId`, which skips the page cache and left the head of the chain showing no thread.

**Where extra pictures come from.** Google Images cannot be scraped (no API, results are blocked), so widen the search through pages that carry the pictures: the retailer or blog page for that exact item (`og:image` from a plain `curl -A "<browser UA>"`; skip a site's generic placeholder image, e.g. Nice Kicks' `IMG_1350.png`), the maker's own launch coverage, and the lead image of each referenced article. The featured `og:image` is the cropped upload (`...-scaled-e<digits>.jpg`), not the `srcset` thumbnails.

# Quality bar

A draft is ready to save when:

- `title` names the event ("... Opens", "... Premieres"), under about 80 characters, without a site name.
- `description` is one or two plain sentences leading with the concrete detail a reader would remember.
- `utcStartDateTime` and `dateConfidence` are set, and `dateConfidenceReasoning` quotes the wording that decided it.
- A delayed event carries `originalStartDate` and `delayReasoning` (`Stated:` or `Estimated:`).
- `categories` has at least one value from the list, and `company` is set when a single organisation fits.
- `sourceUrl` is the source's own URL, not a shared roundup.
- `references` holds every reference at confidence 70 or more (never more than 5), and none is the source.
- 3 media reached by best effort, with at least 1 video and at least 1 picture among them; fewer, or no video, only when every source was tried, with what was tried noted.
- A game pin carries its aggregated ratings, its maturity rating with content descriptors and its supported platforms, each read from a fetched page (see [Game facts](#decision-rules)).
- A prediction-market pin says what its markets have traded, in dollars, next to the odds it quotes.
- The `longFormSummary` is an HTML bulleted list whose every point cites what backs it.
- The pin passes the [value test](#principles) (principle 9). Its summary is original synthesis from more than one source and gives context beyond the source page; no sentence is lifted from the source except a short, attributed quote; and it is not interchangeable with a sibling pin in the same batch.
- A model or product pin carries the maker's main results table (`<h3>Benchmarks</h3>` + `<table>`) when one is published.
- A consumable food, snack or beverage product pin carries its native 7-axis taste rubric (`PinTaste` via `PUT /api/pins/:id/taste`) with editorial estimate scores, basis, and at least one verified firsthand tasting review (`PinTaste.reviews`), kept synchronized in `scripts/products/taste.json`.
- An attendable event pin (concert, festival, sports fixture, conference) carries a `PinEventInfo` ticket reading when the organiser's or ticketer's own page is readable - a `ticketUrl` to that show's purchase page once it is on sale, never guessed.


# When the API is out of credit

Only stages 2 and 3 call Claude. Without a key or credit the scrape still runs every other stage. Stage 2's fields fall back to what the page's own markup states ([metadata.ts](../../../src/server/scrape/metadata.ts): the title with the site name stripped, the description, an Event's start date as `scheduled` or the publish date as `unknown`, an Event's place, a Product's price, keyword tags; never a company, category or coordinates). The scrape response then carries `llm: "session"` and `llmTasks`: the extraction and the reference search, each with the app's own system prompt, JSON schema and input. A Claude Code session answers them and saves through the same route: [Scrape without credit](../playbooks/scrape-without-credit.md).
